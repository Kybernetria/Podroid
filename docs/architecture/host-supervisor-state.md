# Persisted Host supervisor state (tickets #10–#11)

The Android Host owns one app-private, credential-protected `host_supervisor_state` Preferences DataStore. It is separate from UI/settings preferences, contains one strict atomically replaced record, and is excluded from backup/device transfer.

Schema v3 retains the v1 desired-state/transaction fields and v2 bounded reconciliation evidence, then adds sticky `runtimeMayBeLive` evidence with a monotonic evidence version. The repository migrates v1 through the v2 shape and v2 to v3 within one atomic DataStore update, conservatively deriving possible-live state from interrupted reconciliation and lifecycle-effect evidence; every legacy REMOVE outcome remains possible-live because those removals lacked a fixed-runtime absence proof, while a definitive successful STOP/FORCE_STOP takes precedence. Missing v0 initializes fail-safe disabled/stopped defaults. Unknown future versions, malformed records, and invalid cross-field combinations fail closed without replacing evidence. Delayed skip or superseded results cannot clear newer possible-live evidence; only successful authoritative fixed-runtime cleanup, explicit stop, or a current REMOVE that performed the same fixed-runtime preflight before deletion can clear it and advance the evidence version.

A process death that leaves the latest lifecycle transaction `PENDING` is first resolved as `FAILED/PROCESS_DIED` and reconciliation records `INTERRUPTED`. Only then may reconciliation prepare a fresh `RECOVER` transaction through `VmManager`. Successful lifecycle commands reset durable backoff. Failed reconciliation uses bounded exponential delay (5 seconds through a 15-minute cap) and stops after five consecutive attempts. Before each remaining attempt the service installs one explicit, inexact `setAndAllowWhileIdle` alarm at the persisted next-eligible epoch, including cleanup-only retries when possible-live evidence survives stopped or disabled Host intent; success, definitive absence, supersession where appropriate, and exhaustion cancel it. No exact-alarm permission is requested. Persisted values contain no exception text, path, credential, or arbitrary message.

Triggers are deliberately distinct:

- `BOOT_COMPLETED` restores any persisted retry alarm, starts normal recovery only for Host enabled + autostart + desired `RUNNING`, and also starts cleanup-only supervision when sticky possible-live evidence exists. Because the DataStore is credential protected, no direct-boot/locked-boot receiver is registered.
- a `START_STICKY` null-intent service recreation and a durable retry alarm reconcile enabled desired `RUNNING` regardless of autostart;
- explicit desired `STOPPED` never launches.

Android force-stop is respected. Force-stop suppresses manifest receivers, sticky service recreation, and alarms; Podroid does not attempt to bypass it. Opening the launcher never dispatches recovery. Reconciliation resumes only when the user explicitly taps **Start VM** (or a later normal boot trigger is eligible).

Before every new manager-owned generation and every explicit STOP/FORCE_STOP completion, fixed-name probes inspect both one-active-VM backends. QEMU requires a valid alive pid/start-ticks owner record; each query/quit connection then authenticates `SO_PEERCRED` to the app UID and the same owner PID and rechecks `/proc` start ticks before sending QMP bytes. AVF uses the fixed `podroid` framework VM name. A live orphan cannot be safely adopted, so it receives a bounded authenticated typed quit/stop and must become absent before completion. Missing/corrupt/mismatched ownership is uncertain (or dead-owner stale when exact death is proven), never a quit target. Stale Unix endpoints are deleted only after confinement, NOFOLLOW type, owner, and identity checks.

The existing `VmManager` launch-plan path restores persisted and implicit port forwards. A separate `HostTransportReconciler` seam runs after runtime reconciliation; its ticket-#11 production binding is an explicit successful `NO_CONFIGURED_TRANSPORT` no-op until ticket #15.

One process-local reconciler runs at a time. Foreground notification and WakeLock are established before reconciliation work, released when no work/runtime remains, and retained for a live or non-quiescent runtime.
